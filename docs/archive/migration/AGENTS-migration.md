# AGENTS.md

本文件是 Agent 进行项目迁移阶段的指导。项目迁移进行到 P5 阶段时需要归档本文档，将原本的AGENT.md改写至本文件中。

## 文档

| 文档 | 唯一负责的内容 |
|---|---|
| `docs/plans/new-structure-description.md` | 仓库迁移重组的总体指南 |
| `docs/plans/p{0-9}-{plan|report}.md` | 仓库迁移重组的具体计划和实施报告 |
| `docs/plans/p5-ref-doc-refactor-guide.md` | 用户咨询另一个 LLM 得到的 P5 执行指南 |

## 工作规则

- 决策改变时，同一次改动里更新相关文档。`README.md` 和本文件保持简短——用户会经常手改。
- **一件事只详细写一次。** 详细内容只放在它的归属文档里（见上表）；其他文档写一句加链接。发现重复时：先确定归属，把细节收敛到那里，其余地方改成引用，不要两边各写一遍。
- **测试只增不减是缺陷，不是勤勉。** 改行为时顺手检查：新用例是否让旧用例变得重叠？被更强用例覆盖的旧用例要**在同一个提交里删掉**，不要为"多几个 green"留着。判据是"这条规则有没有更强的地方在管"，不是用例数。同一交付里同时出现"新增测试"和"删除测试"是正常的好提交。
- **文档只增不减是缺陷。** 改动引入新细节时，同一个提交里必须删掉被它取代的段落。加进卡片的每一行，都要能回答“删掉它 agent 会做错什么”。叙事、动机、历史、未来计划不进卡片和 reference，只进 docs/decisions、plans、archive。卡片超预算时，删内容或把细节搬到 reference，不许放宽阈值。

## 与用户的协作方式

- 遇到不确定的事情尽快询问用户。多问问题是受欢迎的行为。
- 充分利用git功能。一个阶段的工作完成后立即提交。小改动直接提交到 `{{main/默认分支}}`；较大改动先 `git switch -c {{type}}/{{slug}}`，验收通过后再合回。

### 智能体团队

- 主会话（Lead）负责设计：读文档、定方案、拆分任务、分配写作用域、最终 review 与提交。
- 子 agent 负责执行：按任务边界改代码/文档，自检后回报；写作用域互不重叠，同一文件由 Lead 串行安排。
- 较大阶段用共享任务板跟踪：`write_scopes` 标预期写的文件，`blocked_by` 标依赖。
